PHASE 1F-C
Viral Magic OS — Solution Recommendation Testing, Polish, and Stabilization

OBJECTIVE

Complete Phase 1F-C by testing, polishing, and stabilizing the Phase 1F Solution Recommendation system for Version 1.0.

Phase 1F-A and Phase 1F-B are complete.

This phase is not for adding major new features.

Primary goals:

1. Eliminate known warnings and small defects
2. Verify the full recommendation workflow end to end
3. Improve reliability, clarity, and usability
4. Confirm responsive behavior
5. Confirm accessibility basics
6. Confirm no regressions across Phase 1A–1F
7. Produce a final Phase 1F completion report

STRICT SCOPE

Work only on testing, repair, polish, and stabilization.

Do not:

- Start Phase 1G
- Add billing
- Add client portals
- Add exports
- Add PDF generation
- Add print-specific features beyond fixing existing behavior
- Add AI-generated recommendations
- Add external APIs
- Add new database tables unless required to repair a verified defect
- Redesign the application
- Replace the deterministic recommendation engine
- Change recommendation scoring logic unless a verified bug is found
- Perform broad refactors
- Add unrelated features

SECTION 1 — FULL END-TO-END RECOMMENDATION WORKFLOW TEST

Test the complete workflow through the application UI and API.

Use a dedicated test client/project/assessment where possible.

Verify:

1. Open an approved Growth Assessment
2. Generate a Solution Recommendation Plan
3. Confirm the plan is created in draft status
4. Confirm the plan appears in:
   - Growth Assessment Recommendations tab
   - Client Overview
   - Project Diagnostics
   - Dashboard Recent Plans
5. Open the recommendation detail page
6. Confirm all seven tabs load correctly:
   - Executive Recommendation
   - Priority Recommendations
   - Action Plan
   - Business Impact
   - Dependencies
   - Consultant Notes
   - Approval
7. Edit draft-level fields
8. Save edits
9. Reload and confirm persistence
10. Edit per-recommendation admin notes
11. Reload and confirm persistence
12. Submit the plan for review
13. Confirm awaiting_review status
14. Confirm draft-only fields become read-only where intended
15. Approve the plan
16. Confirm approved status
17. Confirm approval validation blocks approval when required fields are missing
18. Reopen the approved plan
19. Confirm reopened status allows editing
20. Regenerate the plan
21. Confirm the prior plan becomes superseded
22. Confirm the new plan becomes current
23. Confirm regeneration is atomic
24. Archive a valid test plan
25. Confirm archived plans remain viewable but read-only
26. Confirm activity history records all lifecycle events

Document every tested transition and result.

SECTION 2 — STATUS AND PERMISSION VALIDATION

Verify the correct actions are available in each status.

Draft:

- edit
- submit
- regenerate
- archive, if designed
- approve should not bypass required validation

Awaiting review:

- approve
- reopen if supported
- archive if supported
- editing restrictions enforced

Approved:

- read-only
- reopen
- regenerate if supported
- archive if supported

Reopened:

- editable
- submit
- approve after validation
- regenerate

Superseded:

- read-only
- clearly labeled
- cannot be accidentally edited or approved

Archived:

- read-only
- clearly labeled
- excluded from current-plan displays where intended

Confirm UI permissions and API permissions agree.

Test direct API calls for prohibited transitions to ensure backend enforcement exists and the UI is not the only protection.

SECTION 3 — DATA INTEGRITY AND ENGINE VALIDATION

Verify:

- Recommendation priorities are ranked consistently
- Priority scores remain in the 0–100 range
- Classification bands display correctly
- Recommendations link to the correct assessment
- Client and project relationships are correct
- Actions belong to the correct recommendation
- Dependencies reference the correct recommendation records
- No duplicate current plans exist after regeneration
- Superseded plans are preserved
- Activity entries are timestamped and ordered correctly
- Empty optional fields do not crash rendering
- Missing related records return controlled errors
- Invalid IDs return 404
- Invalid request bodies return 400

- Approval validation returns a clear error response

Do not change scoring rules unless a real deterministic bug is reproduced.
