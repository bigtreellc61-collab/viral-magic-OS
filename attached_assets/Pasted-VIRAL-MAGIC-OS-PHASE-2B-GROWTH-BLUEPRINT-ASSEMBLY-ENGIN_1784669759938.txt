1. BLUEPRINT VERSIONING AND SOURCE SNAPSHOT
==================================================

Formalize Blueprint versioning before adding generated content.

Each Growth Blueprint must include or support:

- version number
- revision number if appropriate
- parentBlueprintId or previousVersionId
- isCurrent
- source assessment ID
- source recommendation plan ID
- source assessment status
- source recommendation-plan status
- generatedAt
- approvedAt
- source snapshot metadata
- supersededAt where applicable

Recommended display format:

- Version 1.0
- Version 1.1
- Version 2.0

Version behavior:

A. First Blueprint created from an approved recommendation plan:
- version 1.0
- draft
- current version

B. Regenerating a draft or in-progress Blueprint:
- update the same Blueprint only when explicitly requested
- preserve consultant-edited fields that are marked as overrides

C. Revising an approved Blueprint:
- do not overwrite it
- create a new draft version
- link it to the previous approved Blueprint
- mark the prior version as superseded only when the new version is approved
- preserve prior approved content

D. Archived Blueprint:
- remains read-only
- cannot become current without creating a new version

Do not overengineer semantic versioning.

Use the smallest model that supports:

- historical versions
- current version
- revisions after approval
- traceability
